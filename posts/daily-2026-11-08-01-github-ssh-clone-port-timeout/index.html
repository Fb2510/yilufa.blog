GitHub 网页能打开，克隆却超时？先查 SSH 端口

一路發2026-11-08— 次阅读
网络教程

GitHub 网页能打开，克隆代码却一直超时，可以先检查传输方式。克隆是把远程仓库复制到电脑，SSH 是用于加密连接和身份验证的协议。本文适用于已安装 Git、OpenSSH，并已把 SSH 公钥加入 GitHub.com 账户的电脑。公钥用于验证身份，私钥留在自己设备上。连接准备

先确认连接到哪里

已有本地仓库时，在仓库目录运行 git remote -v，查看远程地址。以 git@github.com 开头的常见地址使用 SSH，以 https:// 开头的地址使用 HTTPS。后者报错时应沿 HTTPS 路径排查。准备首次克隆的人，可在仓库页面的 Code 菜单核对所选方式。远程地址说明 · 查看远程配置

对照两个连接端口

先在终端运行 ssh -T git@github.com，默认连接 22 端口。若已自定义 SSH 配置，用 ssh -vT git@github.com 查看实际目标与端口。出现 Permission denied (publickey) 时，优先核对正在使用的密钥及其账户归属。认证排查

若连接超时，再试 ssh -T -p 443 git@ssh.github.com。这里的主机名是 ssh.github.com，端口改为 443 后仍使用 SSH 协议。GitHub 提醒，代理服务器仍可能干扰这种连接。443 端口说明

首次连接会询问是否信任主机，先将显示的指纹与官方列表比对，相符后再确认。指纹是辨认服务器密钥的短标识。成功信息应包含你的用户名，提示不提供命令行登录属于预期结果。官方指纹 · 成功提示说明

若 22 超时而 443 成功，可优先检查端口策略与分流规则。两者都超时，则把同一条命令放到另一条可用线路上复测。每次只改一个条件，记录时间、节点和报错，才能判断是哪一步恢复。

验证实际克隆路径

443 测试成功后，可按官方格式 git clone ssh://git@ssh.github.com:443/OWNER/REPOSITORY.git 克隆，将 OWNER 和 REPOSITORY 换成仓库所有者与仓库名。身份验证成功后仍报仓库不存在，就检查地址和访问权限。本文路径针对 GitHub.com，企业自建实例需查其文档。克隆格式 · 克隆错误说明

检查翻墙网络时，在代理客户端的连接记录里确认这次终端请求是否经过所选节点。浏览器与终端可能采用不同路径。固定节点地区和仓库，记录克隆耗时以比较节点速度，再于晚高峰复测，观察中断次数来判断线路稳定性。比较时保留仓库版本与下载大小，避免把文件变化算成速度变化。

再判断套餐是否够用

网络延迟可用同一路径的往返探测观察，丢包表现则记录发包数、未响应次数及目标，超时可能包含探测被过滤的情况。另用自己的账号播放指定影片，并完成一次海外 AI 对话，分别记录流媒体解锁和 AI 服务可用性。

挑选便宜机场时，把套餐价格、流量倍率和克隆失败后的额外消耗一起比较。先用短期套餐完成常用仓库的下载验证，再决定是否续费。保留失败阶段和端口对照记录，也能帮助客服定位问题。
